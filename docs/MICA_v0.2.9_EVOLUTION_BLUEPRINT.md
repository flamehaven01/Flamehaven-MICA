# MICA v0.2.9 Evolution Blueprint

## Status

Design blueprint only. Not yet approved or released.

Central judgment: v0.2.9 should not turn MICA into a generic memory engine.
It should evolve MICA into a governed memory operating layer:

- external memory systems may provide observation, retrieval, replay, and adapter machinery
- MICA remains the authority on contract truth, provenance, promotion, and auditability

This revision incorporates peer-review feedback where it materially improves buildability,
trust boundaries, and state-machine clarity. Feedback that would bloat v0.2.9 scope without
improving the first shipping cut is deferred explicitly.

---

## Scope decision

v0.2.9 is the first observation-to-promotion release, not the final memory stack.

### In scope for v0.2.9

- append-only observation log
- candidate registry
- promotion provenance rules
- redaction policy with audit-safe identity preservation
- flow-state reporting separated from core-state reporting
- minimum enforceable PCTs required to keep flow honest

### Deferred beyond v0.2.9

- full hybrid retrieval sidecar
- broad MCP / adapter ecosystem
- benchmark harness and replay leaderboard
- graph query DSL
- production viewer / replay UI

The rule is simple: v0.2.9 ships the governed promotion pipeline first.
Retrieval sophistication can arrive later.

---

## Why v0.2.9 is needed

MICA v0.2.8 is strong at memory governance:

- composition contract (`mica.yaml`)
- archive / playbook separation
- DI binding truthfulness checks
- lesson-ref integrity checks
- freshness signaling
- honest loaded-state reporting (`CLOSED`, `INCOMPLETE`, `LEGACY`, `INACTIVE`)

But it is still weak at operational memory flow:

- no native observation log
- no candidate lesson queue
- no promotion pipeline from raw session evidence to archive-grade memory
- no recall trace
- no adapter trust model
- no governance-aware memory metrics

v0.2.9 closes the first half of that gap: it introduces evidence capture and promotion
control, while deliberately postponing retrieval ambition.

## Core architectural boundary

### MICA-Core remains the control plane

MICA-Core answers:

- What counts as a valid memory package?
- Which assets are required?
- Which claims are grounded in real episodes?
- Which lessons and bindings are approved truth rather than unreviewed suggestions?
- When is a package honestly CLOSED versus merely useful or noisy?

### MICA-Flow is optional operational machinery

MICA-Flow handles:

- observation capture
- candidate generation
- recall tracing
- promotion proposals
- optional adapter ingress

This creates a two-plane model:

| Plane | Role | Truth criterion |
|---|---|---|
| `MICA-Core` | Contract, archive, playbook, PCT | Structural and provenance truth |
| `MICA-Flow` | Observe, propose, trace | Operational usefulness under governance |

Important rule:

> Retrieved or observed memory is never governed truth by default.
> Promotion is the boundary.

## Accepted design corrections from review

### 1. Redaction must preserve audit identity

Peer-review finding accepted.

`observe_policy.redact_secrets: true` must not destroy the identities needed by promotion.
Therefore redaction policy is clarified:

- payload fields MAY be masked, dropped, or replaced
- `event_id`, `timestamp_utc`, `session_id`, `scope`, `event_hash`, and `prev_event_hash` MUST remain stable
- source references MUST survive redaction
- promotion may rely on redacted observations as long as identity and integrity fields remain intact

This resolves the redaction ↔ provenance conflict by making payload confidentiality subordinate to
identity-preserving auditability at the metadata layer, while still protecting secret content.

### 2. Adapter trust must be explicit

Peer-review finding accepted.

If external adapters can inject observations, MICA-Core truth cannot quietly inherit their output
without a trust model. v0.2.9 therefore introduces trust tiers for imported observations:

- `native` — generated by MICA-owned hook writers
- `attested` — external source whose import record passes the v0.2.9 attestation minimum
- `opaque` — externally supplied observation without attestation

Promotion policy may forbid `opaque` observations from becoming Stage 3 binding evidence.

### 3. Static and runtime PCTs must be treated as separate tracks

Peer-review finding accepted.

The blueprint previously grouped file-verifiable and runtime-verifiable checks into one undifferentiated
family. v0.2.9 corrects this:

- static PCTs are evaluated from package artifacts alone
- runtime PCTs require flow telemetry or live hook traces

The numbering remains sequential for continuity, but implementation is split into two validator tracks.

### 4. `enabled` and `required` must be distinct

Peer-review finding accepted.

v0.2.9 defines them explicitly:

- `enabled`: flow machinery is configured and should run if available
- `required`: truthful package operation depends on that flow machinery being present and healthy

A package may be `enabled: true` and `required: false`.
That package may report `FLOW_DEGRADED` without making Core invalid.

### 5. Long-lived records need explicit versioning

Peer-review finding accepted.

- every line in `mica.observe.jsonl` and `mica.recall.jsonl` must carry `schema_version`
- `mica.candidates.json` must carry `schema_version` at the document root

### 6. GC must respect promotion dependencies

Peer-review finding accepted.

If an observation is referenced by a candidate, approved lesson, or DI binding evidence, retention must
not silently delete it. v0.2.9 therefore adopts a mark-and-sweep rule:

- observations referenced by Stage 1-3 artifacts are pinned
- if payload deletion is required, a tombstone record with identity and integrity metadata must remain
- promotion references may never dangle

### 7. Operator review and agent-context injection must be separated

Peer-review finding accepted.

A candidate shown to an operator is not equivalent to a candidate injected into an agent context.
Therefore recall traces must distinguish the target surface explicitly.

### 8. Metrics are not all gates in v0.2.9

Peer-review finding partially accepted.

Metrics are valuable, but v0.2.9 should not over-promise automatic threshold governance everywhere.
Therefore:

- zero-tolerance policy checks may gate immediately, such as unapproved candidate injection
- broader quality metrics begin as observational, not blocking
- promotion gates in v0.2.9 stay provenance-first rather than benchmark-first

This keeps the first release implementable.

## Trust-tier model

### Attestation minimum

An imported observation may be labeled `attested` only if all of the following exist:

- `source_system`
- `source_event_ref`
- `imported_at_utc`
- `event_hash`
- integrity validation result recorded at import time

Additionally, at least one of the following must hold:

- signed import envelope verified by a trusted key
- append-only hash-chain continuity verified for the imported upstream segment
- explicit allowlisted adapter with a deterministic import contract and successful integrity check

If none of these conditions hold, the observation is `opaque`, not `attested`.

### Promotion rule

- `native` evidence may be promoted if other provenance requirements are met
- `attested` evidence may be promoted if other provenance requirements are met
- `opaque` evidence may inform candidate generation but may not become Stage 3 binding evidence

This is the minimum trust boundary for v0.2.9.

## Artifact model

v0.2.9 adds optional assets beneath the archive/playbook layer.

| Asset | Format | Role | Required in v0.2.9 |
|---|---|---|---|
| `mica.observe.jsonl` | NDJSON | Append-only observation stream | Yes when `flow_policy.enabled=true` |
| `mica.candidates.json` | JSON | Candidate registry and promotion queue | Yes when `flow_policy.enabled=true` |
| `mica.recall.jsonl` | NDJSON | Recall trace log | Optional in v0.2.9 |
| `memory/replays/` | Directory | Replay corpora for later evaluation | Optional |

Because `mica.candidates.json` is a mutable document rather than an append-only stream, versioning is
root-level: the file itself MUST carry `schema_version`.

The existing required assets remain unchanged:

- `mica.yaml`
- archive JSON
- playbook markdown

This preserves backward compatibility.

## Proposed `mica.yaml` extensions

v0.2.9 should extend `mica.yaml` with optional flow declarations.

```yaml
flow_policy:
  enabled: true
  required: false
  observation_log: memory/mica.observe.jsonl
  candidate_registry: memory/mica.candidates.json
  recall_trace_log: memory/mica.recall.jsonl

observe_policy:
  capture_hooks:
    - session_start
    - post_tool_failure
    - file_edit
    - session_end
    - operator_decision
  redact_secrets: true
  redaction_identity_policy: preserve_ids_hashes
  max_event_bytes: 32768

promotion_policy:
  inject_unapproved_candidates: false
  candidate_to_lesson_requires:
    - source_event_ids
    - observed_at_utc
    - project_scope
    - operator_review
  candidate_to_binding_requires:
    - origin_episode
    - supporting_event_ids
    - operator_review
    - trust_tier_attested_or_native

integration_policy:
  adapters:
    - kind: observation_import
      name: external_memory_sidecar
      required: false
      attestation_mode: hash_chain_preferred
```

Design principles:

- all new blocks are optional
- `required` is explicit and never inferred from `enabled`
- retrieval is not normative for v0.2.9
- promotion is provenance-first

## Normative record shapes

These are minimum shapes, not exhaustive examples.

### Observation record (`mica.observe.jsonl`)

```json
{
  "schema_version": "mica.observe.v1",
  "event_id": "obs_20260707_000123",
  "timestamp_utc": "2026-07-07T04:12:31Z",
  "session_id": "sess_001",
  "hook": "file_edit",
  "actor": "ai_maintainer",
  "scope": {
    "project": "verification-ledger",
    "paths": ["memory/verification-ledger-playbook.md"]
  },
  "summary": "Updated provenance fallback rule.",
  "redaction": {
    "applied": true,
    "policy": "default_opsec"
  },
  "trust_tier": "native",
  "source_system": "mica",
  "event_hash": "sha256:...",
  "prev_event_hash": "sha256:..."
}
```

Required semantics:

- `schema_version` is mandatory
- `event_hash` is mandatory
- `prev_event_hash` is mandatory except for the first record in a stream segment
- redaction may alter payload content, never identity or integrity fields

### Candidates document (`mica.candidates.json`)

```json
{
  "schema_version": "mica.candidates.v1",
  "candidates": [
    {
      "candidate_id": "cand_00042",
      "stage": "candidate_memory",
      "source_event_ids": ["obs_000120", "obs_000121"],
      "claim": "Metric labels that fail provClassOf must not silently render without review.",
      "target": "playbook_lesson",
      "status": "pending_operator_review",
      "risk": "public_surface_misclassification",
      "trust_basis": "native_observation_trace",
      "observed_at_utc": "2026-07-07T04:12:31Z",
      "project_scope": "verification-ledger",
      "operator_review": {
        "state": "pending",
        "reviewed_by": null,
        "reviewed_at_utc": null,
        "decision_reason": null
      }
    }
  ]
}
```

Required semantics:

- the document root must carry `schema_version`
- every candidate must cite `source_event_ids`
- review provenance is part of the MVP, not a later migration

### Recall trace record (`mica.recall.jsonl`)

```json
{
  "schema_version": "mica.recall.v1",
  "trace_id": "rec_00007",
  "timestamp_utc": "2026-07-07T05:00:00Z",
  "target": "operator_review",
  "items": ["cand_00042"],
  "contains_unapproved_candidates": true,
  "justification": "operator triage queue"
}
```

`target` must be one of:

- `operator_review`
- `agent_context`

This field is mandatory whenever recall traces are enabled.

## Promotion ladder

v0.2.9 formalizes four stages.

### Stage 0 — Observation

Raw event captured from hooks or imported logs.

Properties:

- append-only
- timestamped
- hashed
- redactable at payload level
- not archive-grade

### Stage 1 — Candidate memory

Operationally useful summary or cluster derived from observations.

Properties:

- may be surfaced to operators
- may not claim invariant truth
- must cite `source_event_ids`

### Stage 2 — Approved lesson

Human-reviewed lesson with durable procedural value.

Properties:

- allowed into playbook-linked memory
- eligible for lesson references
- must record review provenance

### Stage 3 — Bound invariant evidence

A lesson or episode promoted into DI-supporting evidence.

Properties:

- may populate `binding.origin_episode`
- may increment `violation_count`
- must retain trace to supporting observations
- may not originate from `opaque` trust-tier evidence

This is the core MICA distinction:

> Useful memory may be recalled early.
> Governed memory must be promoted deliberately.

## PCT model for v0.2.9

### Static validator track

| Check | Status model | Purpose |
|---|---|---|
| `PCT-013` | INFO/FAIL | Observation log present, parseable, and hash-chain coherent when flow is enabled |
| `PCT-015` | INFO/FAIL | Promoted lessons / bindings cite valid source-event provenance |
| `PCT-016` | INFO/WARN/FAIL | Adapter declarations are structurally coherent; required adapters resolve |

### Runtime validator track

| Check | Status model | Purpose |
|---|---|---|
| `PCT-014` | INFO/WARN | Recall trace exists when recall injection is active |
| `PCT-017` | INFO/FAIL | No unapproved candidate enters `agent_context` when policy forbids it |
| `PCT-018` | INFO/WARN | Runtime flow telemetry completeness for enabled flow packages |

Recommended semantics:

- `PCT-013` is `FAIL` when `flow_policy.enabled=true` and the observation log is absent, invalid, or hash-chain incoherent
- `PCT-015` is `FAIL` when any approved lesson or bound evidence lacks source trace, points to missing/tombstoned identity incorrectly, or uses `opaque` evidence for Stage 3
- `PCT-016` is `FAIL` only when an adapter is declared `required=true` and cannot resolve
- `PCT-017` is `FAIL` when unapproved candidates appear in `agent_context`
- `PCT-014` and `PCT-018` begin as non-blocking telemetry checks

## Runtime states and transitions

v0.2.9 keeps core state and flow state separate.

### Core state

- `CLOSED`
- `INCOMPLETE`
- `LEGACY`
- `INACTIVE`

### Flow state

- `FLOW_OFFLINE`
- `FLOW_ENABLED`
- `FLOW_DEGRADED`

### State definitions

- `FLOW_OFFLINE`: flow not enabled, or enabled but intentionally not running and not required
- `FLOW_ENABLED`: enabled and minimum required flow assets are healthy
- `FLOW_DEGRADED`: enabled but one or more flow assets are unhealthy or fail their health threshold

### Transition rules

- `enabled=false` -> `FLOW_OFFLINE`
- `enabled=true` and observation/candidate assets healthy -> `FLOW_ENABLED`
- `enabled=true` and any required flow asset unhealthy -> `FLOW_DEGRADED`
- `required=false` and `FLOW_DEGRADED` does not invalidate Core
- `required=true` and a failing flow PCT may invalidate overall package completeness

### Health-threshold guidance for v0.2.9

- missing observation log or unreadable candidate registry -> immediate degradation
- required adapter health-check timeout greater than 30 seconds for two consecutive checks -> degradation
- observation writer integrity failure (hash recompute mismatch) -> immediate degradation

Recommended runtime report shape:

```text
Core: CLOSED
Flow: FLOW_ENABLED
Observation: PASS
Candidates: 3 pending, 1 approved
Recall: OFFLINE
Promotion gate: PASS
```

This avoids confusing optional-flow degradation with core contract failure.

## Retention and GC policy

Observation is cheap, but references must not dangle.

v0.2.9 therefore adopts the following rule:

- unreferenced observations may be GC-eligible under retention policy
- referenced observations are pinned while any candidate, lesson, or bound evidence cites them
- if payload deletion is required for privacy or storage, a tombstone must remain with:
  - `event_id`
  - `timestamp_utc`
  - `scope`
  - `event_hash`
  - `prev_event_hash`
  - redaction / tombstone reason

Mark-and-sweep is the expected implementation model.

## Metrics for v0.2.9

v0.2.9 introduces metrics, but only a subset are gate-coupled immediately.

### Immediate gate-coupled metric

- `unapproved_injection_rate`

Expected value under default policy:

- exactly `0`

Any non-zero value should surface through `PCT-017`.

### Observational metrics in v0.2.9

- `grounded_recall_rate`
- `false_recall_rate`
- `stale_recall_rate`
- `promotion_precision`
- `binding_trace_coverage`
- `closed_truth_preservation`

These are initially report-only. Threshold gates may be introduced in a later release,
after labeling and review workflows are better defined.

## Buildability notes

The following implementation constraints are explicit in v0.2.9.

### Labeling for `false_recall_rate`

`false_recall_rate` is not automatically authoritative in v0.2.9.
It requires post-hoc operator review or later benchmark labeling.
Therefore it is observational only.

### Retrieval breadth is not normative in v0.2.9

Early drafts used illustrative constants such as `max_recall_items`. Those constants are removed from the
normative surface. Retrieval breadth tuning is deferred until recall is a first-class v0.2.10+ concern.

### PCT-016 is intentionally delayed as a full maturity gate

During the first v0.2.9 implementation window, packages may declare optional adapters that are not yet
subject to a full adapter-maturity regime. This is an accepted temporary risk because:

- `required=false` optional adapters do not invalidate Core
- `opaque` trust-tier evidence is barred from Stage 3 promotion
- imported observations still need integrity metadata even before full adapter maturity

This is explicit technical debt, not accidental omission.

### Recall surface separation is defined at schema time

`operator_review` versus `agent_context` is defined before viewer or retrieval expansion.
This avoids avoidable stream migrations later.

## Recommended implementation order

### Phase 1 — Observation foundation

Ship first:

- `flow_policy`, `observe_policy`, and `promotion_policy` schema
- observation log writer and parser
- integrity envelope (`event_hash`, `prev_event_hash`)
- redaction identity rules

### Phase 2 — Candidate registry

Ship second:

- candidate registry schema
- source-event references
- operator review state model
- retention pinning rules

### Phase 3 — First flow PCTs

Ship third:

- `PCT-013`
- `PCT-015`
- `PCT-017`
- runtime status split (`Core` vs `Flow`)

### Phase 4 — Recall trace

Ship fourth:

- recall trace schema
- `target=operator_review|agent_context`
- `PCT-014`

### Phase 5 — Adapters and metrics expansion

Ship later:

- adapter attestation improvements
- `PCT-016` / `PCT-018` maturity
- replay harness
- benchmark gating experiments

---

## Short verdict

> v0.2.9 should ship as the first governed observation-to-promotion pipeline for MICA.
> It should accept external memory-system lessons where they improve traceability,
> trust boundaries, and operational evidence, while refusing to collapse MICA into a
> generic retrieval engine. The first implementation win is not better search. It is
> better governed memory promotion.
